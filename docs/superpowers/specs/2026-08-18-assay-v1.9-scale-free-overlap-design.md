# assay v1.9 — the scale-free overlap rule

2026-08-18. Brainstormed the evening v1.8 merged, from the finding its
own whole-branch review recorded rather than fixed (CARRIED-DEBT item
112, "the 0.25 s tolerance cliff"). Scope confirmed by Brice 2026-08-18:
adopt the scale-free rule, accept the schema bump the field rename
forces. Ships as **0.11.0, profile schema v10**.

One component: `classify_mode` stops asking whether two lanes overlap
by more than a fixed number of seconds and starts asking whether they
overlap by more than a fraction of the shorter lane. The wave's theme:
a scheduling fact should not depend on how fast the endpoint is.

## §0 Scope and non-goals

In scope: the classification rule; the renamed and re-typed field it
records itself with; the schema bump that rename forces; the tests that
pin the new rule at multiple time scales; and the documentation and
carried-debt entries the change invalidates.

Non-goals: **rescoring or re-running the fifteen committed v9 profiles**
— they keep `tolerance_s` and their v9 identity, and the instrument
never rewrites evidence. **Changing the parallel verdict's degradation
floors** (0.8 / 0.5) — untouched, and their own chosen-ness is a
separate open item. **Retiring the `serialized` gate** — this wave makes
that gate *reachable* on fast endpoints, which is the opposite of
retiring it. **Deriving the fraction from measurement** — 0.25 stays
chosen and stays flagged; see §4.

## §1 What is wrong today

`classify_mode` (parallel.py) reads:

```python
for (_, prev_end), (next_start, _) in zip(ordered, ordered[1:]):
    if next_start < prev_end - tolerance:
        return "parallel"
return "serialized"
```

For lanes launched together — which is what `probe_parallel` does — every
span starts at ≈0 and ends at ≈D, so the condition reduces to `D >
tolerance`. **The rule is therefore "each lane must last longer than
0.25 s to count as concurrent."** That is not a statement about the
endpoint's scheduling; it is a statement about the endpoint's speed.

Measured, on genuinely concurrent lanes:

| lane duration | today | correct answer |
| --- | --- | --- |
| 0.05 s | `serialized` | `parallel` |
| 0.222 s | `serialized` | `parallel` |
| 0.3 s | `parallel` | `parallel` |

0.222 s is not hypothetical: it is the pure-decode span computed from
the fastest model on the committed matrix (`qwen2.5-coder-1.5b-instruct-q8_0`,
288 tok/s, `DECODE_MAX_TOKENS = 64`). That row reads `parallel` today
only because prefill and HTTP padded its wall-clock span over the
threshold. Any faster endpoint on this tier falls off the cliff.

The docstring says the tolerance "absorbs the client-side skew between
'the previous lane's reply finished arriving' and 'the next lane's
request went out'." That intent is right and the mechanism is wrong: an
absolute quantity subtracted from a duration-dependent comparison can
only be correct at one time scale. Dispatch skew is milliseconds; 0.25 s
is two to three orders of magnitude larger than the thing it claims to
absorb.

Under v1.8 this was under-claim only — a false `serialized` caps
`verdict.parallel` at `risky`, which is the safe direction. It is still
a wrong rung on a published page, driven by a constant the instrument's
own documentation admits is unexercised.

## §2 The rule

A pair is `parallel` when its overlap exceeds a **fraction of the
shorter span**:

```
overlap   = min(prev_end, next_end) - max(prev_start, next_start)
shortest  = min(prev_end - prev_start, next_end - next_start)
parallel  iff shortest > 0 and overlap > OVERLAP_FRACTION * shortest
```

`OVERLAP_FRACTION = 0.25`. The number is deliberately the same digit the
old constant carried, but it is now dimensionless, and §3 makes sure no
reader or document can confuse the two.

Verified against both failure directions before this spec was written:

| case | today | new rule |
| --- | --- | --- |
| concurrent, 0.05 s lanes | `serialized` ✗ | `parallel` ✓ |
| concurrent, 0.222 s lanes | `serialized` ✗ | `parallel` ✓ |
| concurrent, 1.0 s lanes | `parallel` ✓ | `parallel` ✓ |
| serialized, 0.05 s lanes | `serialized` ✓ | `serialized` ✓ |
| serialized, 1.0 s lanes | `serialized` ✓ | `serialized` ✓ |
| near-miss: 2 ms overlap on a 200 ms lane | `serialized` ✓ | `serialized` ✓ |

The new rule **strictly dominates**: it corrects every case the old one
got wrong and changes none it got right. In particular the near-miss row
is the one that matters for the skew the old tolerance existed to
absorb — 2 ms against a 200 ms span is 1% overlap, far under the 25%
floor, so skew still cannot manufacture a false `parallel`.

The `len(spans) < 2 → None` rule is unchanged: `serialized` is a claim
about how two lanes relate, and one lane relates to nothing. The
`shortest > 0` guard is new and covers a degenerate zero-length span,
which would otherwise make any overlap infinite in ratio terms.

## §3 The field must be renamed, and that forces the schema

`Parallel` records the constant it ran under, and it is serialized into
every profile:

```json
"tolerance_s": 0.25, "tolerance_provenance": "chosen-2026-08-17"
```

Keeping that name would mean a field called *seconds* carrying a
*fraction*. Worse, and this is the load-bearing reason: **assay's own
`diff` would compare `tolerance_s: 0.25` against `tolerance_s: 0.25`,
find them byte-equal, and report no change across a break where the
classification rule changed completely.** A field that reads identical
on both sides of a semantic break is the exact failure the whole
instrument exists to refuse, and it is the same shape as the v1.8 wave's
frozen-corpus pin that compared against a moving `PROFILE_VERSION`.

So:

- `tolerance_s` → **`overlap_fraction`** (dimensionless).
- `tolerance_provenance` → **`overlap_provenance`**, still
  `"chosen-2026-08-18"` — the fraction is chosen, and §4 says what would
  retire it.
- `OVERLAP_TOLERANCE_S` → `OVERLAP_FRACTION`; `TOLERANCE_PROVENANCE` →
  `OVERLAP_PROVENANCE`.
- **Profile schema v9 → v10; package 0.10.0 → 0.11.0.**

The schema bump is not bookkeeping. It is what makes a consumer's
instrument-changed precheck fire on this boundary instead of letting a
diff sail through it — bloomery's drift watch prechecks on
`probe_version` and `schema_version` and will correctly refuse to
compare a v9 reference against a v10 current, which is the honest
outcome for a pair measured under two different rules.

The fifteen committed v9 profiles are **not** rescored and the campaign
is **not** re-run. They keep `tolerance_s` and their v9 identity. A
renderer must therefore tolerate both shapes; a v9 row simply has no
`overlap_fraction`, exactly as a v8 row has no `verdict.parallel` (the
deep-grades precedent).

## §4 What is still chosen, and what would retire it

`OVERLAP_FRACTION = 0.25` is CHOSEN, and `overlap_provenance` says so at
every point of use — the same idiom the degradation floors keep.

What changes is the retirement condition. CARRIED-DEBT item 16 records
that retiring the old constant needed "an endpoint that actually
serializes," because no live row had ever read `serialized`. That is
still true and still open, but the reason it matters is now different:

- The **old** constant was unexercised AND could produce a false
  `serialized` on any fast endpoint. Two problems.
- The **new** fraction is unexercised in one direction only. It can no
  longer produce a false `serialized` from speed alone — §2's table
  shows genuinely concurrent lanes read `parallel` at every scale — so
  what remains unexercised is the boundary itself: no live row has ever
  overlapped by between 0% and 25% of a span.

Item 16 is amended, not closed. This wave narrows what it is waiting
for; it does not satisfy it.

## §5 Consequences to state plainly

**The house fake changes rung.** Its lanes are sub-millisecond, so under
the old rule a full-mode `probe()` read `serialized` and
`verdict.parallel` was capped at `risky` despite a degradation ratio of
~1.0. Under the new rule the fake reads `parallel` and the verdict reads
`ready`. The v1.8 test that asserts `risky` end-to-end must be updated,
and its docstring must explain the change rather than silently flipping
an expectation — that test existed precisely to pin the cliff's effect.

**No committed profile's meaning changes.** Profiles store the derived
`mode`, not the spans, so nothing recorded is reinterpreted. Only future
runs classify differently.

**The `serialized` gate becomes more reachable, not less.** A real
queueing endpoint on a fast box could not previously be distinguished
from a fast concurrent one, because both read `serialized`. After this
wave, `serialized` means what it says.

## §6 Testing posture

House rules apply (TDD; mutation-check each load-bearing test).
Specifically:

- **The rule at multiple time scales, enumerated.** §2's table is the
  test: concurrent and serialized cases at 0.05 s, 0.222 s and 1.0 s,
  plus the near-miss skew row. A rule whose defect was scale-dependence
  must be tested at more than one scale — testing it at one is how the
  original shipped.
- **The near-miss is load-bearing** and must fail if the fraction is
  dropped to near zero: it is the only guard that skew cannot
  manufacture a false `parallel`.
- **`shortest > 0`** exercised with a zero-length span.
- **v9 back-compatibility**: the fifteen committed profiles still load,
  render and diff; a renderer meeting `tolerance_s` does not raise.
- **The end-to-end rung change** (§5) asserted at the `probe()` level,
  with the reason in the docstring.
- **Schema and package versions move together**, the existing
  cross-check.

## §7 Non-goals restated

Nothing here touches the degradation floors (0.8 / 0.5), the refusal
policy, exit 3, or `verdict.parallel`'s ladder beyond the `serialized`
gate's input. Multi-turn chains and pool-to-35 remain untouched and
unowned by this wave.
