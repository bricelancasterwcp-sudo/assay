## §1 The dropped invariant, and the false-drop fix (prerequisite)

`DiffResult.dropped` documents itself as "cells present on one side
only", and four of the five family walkers honor that: `_exact`,
`_diff_codec_cell` and `_diff_speed_cell` all return an empty
`_Cells()` when BOTH sides are absent, dropping only the genuinely
one-sided. `_diff_verdicts` is the odd one out — its guard
(`old_value is None or new_value is None or UNMEASURED in (...)`)
sends both-sides-`None` and both-sides-`"unmeasured"` to `dropped`
too. That is Inbound §2's false drop: a byte-equal
`verdict.long_context` reported as "dropped", reproduced twice during
bloomery's acceptance.

**Fix:** `_diff_verdicts` adopts the sibling idiom — both sides
absent/unmeasured returns `_Cells()`; exactly one side measured
drops. After the fix the invariant is uniform across all five
families and becomes load-bearing:

> **dropped ⇔ the cell was measured on exactly one side.**

This lands BEFORE §2 in plan order, because exit 3 triggers on
`dropped` and must not fire on a display-layer lie. Tests: byte-equal
both-unmeasured verdicts produce no drop and no change; one-sided
verdicts still drop; a regression test pinned to the
`verdict.long_context` repro shape.

## §2 Exit 3 — an incomplete comparison is not a clean one

The measured blind spot (Inbound §1): a v8-vs-v4 pair exits 0 under
`--gate` while five measured families go unmeasured-on-one-side.
Literally true under the current rules — `dropped` never touches the
exit code — and exactly the "green CI check nobody investigates" the
`_load_profile` docstring warns about. The blind spot exists in plain
mode too: five vanished families with nothing else moving is exit 0
either way.

**Contract** (cli.py docstring table, README):

```
0  comparable, and nothing moved beyond noise (--gate: nothing moved
   in the regression direction)
1  drift found (--gate: a REGRESSION was found)
2  not comparable — different model, quant, weight size or hardware
3  incomplete — at least one cell was measured on exactly one side,
   so part of the comparison never happened (NEW)
4  a profile file could not be read or parsed
```

**Trigger:** `result.dropped` non-empty, after the identity gate
passes. No new detection machinery — §1 made `dropped` mean exactly
this. Applies in both plain and `--gate` mode: exit codes are
per-subcommand and 3 is unused by every subcommand.

**Precedence: 2 > 3 > 1 > 0.** The existing ruling is "not comparable
outranks everything: it is the absence of a comparison." Exit 3 is
the partial form of the same fact, so the absence class outranks the
measured class. Exit 1 keeps its precise claim — "a measured number
moved" — which is the standing reason a vanished family could never
ride on it. When a pair has both a dropped family and a measured
regression, the exit is 3 and the prose still lists both; any CI
consumer treats nonzero as red, and one that branches on codes now
learns the truth: this comparison is not whole.

**Render:** one line above the existing `dropped:` list —
`incomplete: N cell(s) measured on one side only` — so the exit code
and the prose tell one story. `DiffResult` and the `--json` document
are unchanged (`dropped` was always there).

**Consequences, named:** a cross-schema pair (v8-vs-v9, v8-vs-v4) now
exits 3, because schema growth measures cells the old instrument
never did — this is the instrument-changed rule ("version mismatch
never scores") enforcing itself at the gate. A budget-vs-full pair of
the SAME schema also exits 3, because families one side never ran are
absent from the comparison. Both readings are intended. bloomery is
unaffected: its version precheck refuses such pairs before diff runs,
and same-version pairs with nothing dropped keep 0/1.

**Tests:** `_diff_exit_code` by enumeration — the full
{dropped∅/dropped≠∅} × {changes: none/improvement/regression} ×
{gate on/off} table, per the process lesson that enumeration catches
what prose review passes. Plus a fixture pair in the bloomery repro
shape (families measured on one side only) asserting the exit flips
0 → 3 in both modes.

## §3 verdict.parallel — mode gates, chosen floors (schema v9)

v1.7 shipped `parallel` measurement-only on the stated ground that a
rung invented without a measured floor is an overclaim. Ninety live
lanes later (15 models × k∈{2,4}, all `mode: parallel`,
`degradation_ratio` 0.995–1.007 across a 10× span of single-lane
speed) the family has evidence to ladder against — and one honest
limitation that shapes the design: **no live row differentiates a
ratio boundary, and no live endpoint has ever read `serialized`.** A
floor "derived" from a cluster at 1.0 would be a fake derivation.
So the floors are CHOSEN and say so, the `OVERLAP_TOLERANCE_S` idiom:
flagged with provenance until an endpoint that actually degrades is
measured.

**The cell.** `verdicts["parallel"]` joins the lens in the
`chat_speed`/`agent_speed` shape:

```
"parallel": {
    "verdict": <ready|risky|unusable|unmeasured>,
    "lens": {"metric": "degradation_ratio",
             "floor_ready": 0.8, "floor_risky": 0.5,
             "floor_provenance": "chosen-2026-08-17",
             "evidence": <weakest class any scored lane produced,
                          or "unmeasured">},
}
```

**The ladder**, in rule order:

1. Any scheduled k skipped/refused, or any measured k whose
   `degradation_ratio` is `None` (no server timings, or no baseline)
   → **unmeasured**. The fleet question is
   "can this box run k agents"; a verdict inferred from the k that
   survived is the overclaim the schema exists to refuse.
   `Parallel.skipped` and `lane_errors` already name why.
2. Any measured k reads `mode: serialized` → **risky at most** (a
   queueing endpoint multiplies every agent's wall-clock by k; its
   per-lane RATE still reads ~1.0, which is exactly why degradation
   floors alone cannot catch it — the scheduling fact gates first).
3. Otherwise ladder the WORST measured k's `degradation_ratio`:
   ≥ 0.8 → **ready**; ≥ 0.5 → **risky**; below → **unusable**.

Floor rationale, recorded: 0.8 sits well below the live cluster
(0.995 minimum over ninety lanes — all fifteen committed models read
`ready`, consistent with how those boxes actually run fleets) and
well above the serialization signature a rate would show if a
server ever did surface queueing in per-lane throughput (~1/k =
0.5 at k=2). 0.5 is that k=2 signature itself. Both are exercised at
their boundaries by NOTHING live; the provenance flag is the promise
to re-derive when something real crosses them.

**Zero new calls.** The verdict derives from measurements the family
already makes: `run.WORST_CASE`, budget mode, and quick's 9-call
margin (CARRIED-DEBT item 43) are all untouched.

**Schema:** `PROFILE_VERSION` 8 → 9, release 0.9.0 → 0.10.0. The
fifteen committed v8 profiles are not rescored and the campaign is
not re-run (§0). A v8 document simply lacks the cell — the deep-
grades precedent (item 14's closure): renderers derive columns from
what a document carries. Invariant: **a v8 profile's render may
change only by gaining an explicitly-unmeasured parallel verdict
cell, and whichever commit changes renderer output re-pins the
matrix byte-identity test in the same commit.** `diff` picks the new
cell up through the existing verdict walk with no code change; a
v8-vs-v9 pair drops it on one side and exits 3 — §2 enforcing the
instrument boundary this cell just moved.

**Tests:** the ladder as a truth table (mode × ratio × skips ×
errors × None-rates), enumerated, not sampled; the lens carries
floors and provenance; and the live pin — parse all fifteen
committed v8 profiles' parallel rows through the new ladder function
and assert every one reads `ready`, so the floors' consistency with
the campaign is enforced rather than asserted.
