# assay v1.6 — the agent surface

2026-08-15. Second of three waves from the 08-14 brainstorm (v1.5
instrument-sharpening SHIPPED → **v1.6 agent surface** → v1.7
consumers + matrix). Ships as **0.7.0, profile schema v6**.

Four components: a native tool-calling probe, an error-recovery script
for the loop probe, MoE-aware geometry metadata, and the v1.5 final
review's consolidation items. The first two close the largest
capability-surface gap for the local-AI agent mission; the instrument
measures what agent frameworks actually consume.

## §0 Scope and non-goals

In scope: one new backend method (`chat_tools`), one new probe family
(`tools`), one new loop script, geometry metadata additions, the
schema/report/diff changes they require, and the ledgered
consolidation debt.

Non-goals (deferred per the approved wave order): time-budgeted
quick-probe mode, parallel degradation, deeper JSON, published matrix
page (all v1.7); sequential look-schedule sampling for the tools
family (fixed-n in v1.6, recorded in the lens; extending the schedule
machinery to two-turn cells is v1.7-at-earliest); text-protocol
tool-calling for endpoints without native tools (measuring a synthetic
protocol no framework uses is the wrong lens — `unsupported` is the
honest verdict); multi-tool-per-turn or parallel tool calls (one
correct call is the v1 question).

## §1 Tool-calling probe

### Backend surface

- New protocol method on `Backend`:
  `chat_tools(messages, tools, *, seed, max_tokens) -> ToolReply`.
  `messages` is the OpenAI/Ollama chat shape (`[{role, content, ...}]`
  including `role: "tool"` result messages); `tools` is the standard
  function-schema list. Both backends implement it: Ollama native →
  `POST /api/chat` with `stream: false`, `think: false`, pinned
  sampler options (seed, `num_predict`, temperature 0.2); OpenAI
  compat → `POST /v1/chat/completions` with `tools`.
- `ToolReply`: `{text, tool_calls, tokens_in, tokens_out, stop_reason,
  raw}` where `tool_calls` is a tuple of `{name: str, arguments:
  dict}` parsed from the response (Ollama: `message.tool_calls[*]
  .function`; OpenAI: `choices[0].message.tool_calls[*].function`,
  whose `arguments` is a JSON **string** and must be parsed — a
  malformed arguments string is DATA, recorded as an invalid call,
  never an exception).
- **Unsupported is data.** A 4xx whose body names missing tool support
  (Ollama: "does not support tools") returns a sentinel the probe maps
  to `tools_supported=False`. Transport failures and other HTTP errors
  stay infrastructure. The classifier keys on behavior class (4xx +
  tools mentioned in the error body), not an exact string — error
  wording is not a stable target.
- `validate_reply`'s count contract applies to tool replies from
  counts-promising backends exactly as to generate replies.

### Instrument (`scripted-tools-v1`)

- Fixed toolset, three schemas, registered here: `read_file(path:
  string, required)`, `run_tests()` (no arguments), `search_docs(
  query: string, required)`. Five heterogeneous task variants, each
  with exactly one obviously-correct tool and, where applicable, an
  exact expected argument value (the task names the file/query
  verbatim, so argument checking is mechanical, not semantic).
- Two scripted turns per task, zero branching on model output:
  - **T1**: system+user messages present the task with the toolset.
    Scored: exactly one tool call emitted; `name` is the correct tool;
    arguments are schema-valid (required keys present, no unknown
    keys, string types) AND match the expected value where the task
    pins one.
  - **T2**: canned continuation — the T1 golden call plus a `role:
    "tool"` result message whose content embeds a seeded **canary
    token** (the ceiling probe's pattern). Scored: reply is a text
    answer containing the canary verbatim AND carries no further tool
    call.
- Cell n = 5 tasks × 1 rep, fixed-n (lens `stopping_rule: "fixed-n"`).
  Metrics: `call_rate`, `right_tool_rate`, `args_valid_rate`,
  `result_use_rate`, each over its scored turns; the **composite** =
  per-task AND of the three T1 criteria, and it is what the verdict
  ladders on.
- Budget: `meter.charge` per call using the established
  chars-per-token proxy over the serialized messages; ~10 calls per
  probe; unmeasured cells are None + dropped, never zero.

### Verdict `tool_calling`

- Ladder on the composite under the house thresholds (0.9/0.6),
  Wilson-95 interval, provisional exactly as the codec verdicts.
- Distinct verdict value **`unsupported`** when the endpoint refused
  the tools parameter: a capability fact — not `unmeasured` (we
  measured the refusal), not `unusable` (the model was never asked).
  `unsupported` cells carry `interval95: None`.
- Lens: `{instrument: "scripted-tools-v1", toolset: "toolset-v1",
  stopping_rule: "fixed-n", n_used, temperature: 0.2}` plus the four
  metric rates. `n_used` absent when unmeasured, as everywhere.
- Diff: the generic verdict comparator ranks `unsupported` BELOW
  `unusable` (ready > risky > degrades-at-N > unusable >
  unsupported); ready→unsupported is a regression `--gate` fails —
  the capability disappeared (daemon/template change). Report renders
  `unsupported` with the unmeasured styling class but the verbatim
  label.

### Falsification tests

- A fake emitting the golden call + canary echo scores composite 1.0
  and `ready` (provisional at n=5); a fake calling the wrong tool
  scores `right_tool_rate` 0 while `call_rate` 1.
- OpenAI-style JSON-string arguments parse; a malformed arguments
  string scores an invalid call (never raises).
- A scripted 4xx tools-unsupported body yields verdict `unsupported`
  with no scored cells; a transport error propagates as
  infrastructure.
- T2 spurious-call and missing-canary cases each fail exactly
  `result_use_rate`.
- Diff: ready→unsupported regression fails `--gate`;
  unsupported→ready improvement passes it.

## §2 Loop error-recovery script

- A second canned script beside the golden path, same envelope, same
  zero-branching rule (`scripted-loop-v2` = golden script + error
  script; the lens instrument string changes, which IS the non-silent
  semantics amendment):
  - T1: unchanged (expect `read`).
  - T2′: the environment shows a canned FAILED patch attempt whose
    SEARCH block carries stripped indentation — the measured qwen
    signature — followed by "The patch FAILED to apply: SEARCH text
    not found in `tiny.py`." and the unchanged file contents, then
    asks for the next action. Scored: **recovery** = the reply is a
    `patch` whose payload applies-and-parses against the original;
    **doom loop** = the reply's SEARCH lines equal the canned broken
    SEARCH when whitespace-normalized (re-emitting the attempt the
    environment just said failed).
- `Loop` gains `recovery_rate: float | None` and `doom_loop_rate:
  float | None` — None when the error script did not run (old
  profiles, budget death before it), never zero.
- `loop_discipline` verdict gains one demotion mirroring the existing
  patch-rate rule: a `ready` drops to `risky` when `recovery_rate` is
  measured and < 0.5. Unmeasured recovery demotes nothing.
- Cost: the error script is its own 2-turn run (T1 + T2′), one per
  `loop_runs`, so the loop family adds 2×runs calls. Budget comments
  recomputed.

### Falsification tests

- A fake that corrects the indentation scores recovery 1.0; a fake
  that re-emits the broken SEARCH scores doom_loop 1.0 and recovery 0.
- Old-profile parse: `Loop(**v5_payload)` constructs with both new
  fields None; serialization round-trip + completeness for the new
  fields.
- ready-with-low-recovery demotes to risky; unmeasured recovery does
  not demote (mutate the guard → tests fail).

## §3 MoE-aware geometry

- KV-cache arithmetic is attention-side and expert-invariant: the
  formula does not change, and `kv_bytes_per_token`'s docstring states
  why (experts live in the FFN weights; K/V heads are dense).
- `ModelInfo` gains `expert_count: int | None` and
  `expert_used_count: int | None` (arch-prefixed metadata keys
  `expert_count` / `expert_used_count`; None for dense models — a
  dense model is not "0 experts", it is not-a-MoE).
- `head_dim` prefers the explicit `attention.key_length` metadata key
  when present; the `embedding_length // head_count` derivation is the
  fallback and its inaccuracy for some GQA/MoE architectures is the
  reason for the preference (recorded in the docstring).
- `Geometry` carries the two expert fields through; `render_table` and
  the report's detail section show a `MoE k-of-n` marker when
  measured. Consumers can now see that a 27B-total model spends like a
  smaller model per token on compute but pays full weights residency —
  the fields make the distinction visible; assay draws no conclusion
  from them in v1.6.
- Live validation: the box's resident MoE model's metadata must
  resolve (expert fields non-None, head_dim from key_length), and its
  KiB/token must match what v1.4's committed profile measured.

### Falsification tests

- A ModelInfo fixture with `key_length` present uses it (mutate the
  preference → test fails); absent → fallback derivation.
- MoE fixture round-trips both fields; dense fixture keeps them None
  (never 0).

## §4 Consolidation (v1.5 final-review debt)

- **One stop-lens mapping.** The codec verdict-lens rule (json_object
  → byte-equality; patch codecs → applies-and-parses) moves to
  `stats.py` as the single registry both `codecs._stop_count` and the
  profile verdict layer consume — the ledgered T2/T3 duplication class
  dies. Behavior unchanged; a test pins that both consumers read the
  shared mapping.
- **`render_table` v1-payload safety.** Bare-string verdicts (schema
  v1) render as their string with no lens line instead of raising
  TypeError. Test against a committed v1 profile.
- **`_lens_title` renders None as "unmeasured"** in the report badge
  tooltip, matching the module's convention.

## §5 Schema, versioning, discipline

- Profile schema **v6**: new `tools` family (dataclass +
  `_FAMILIES` + `.get` back-compat parsing + dropped-naming), `loop`'s
  two new fields, ModelInfo/Geometry expert fields. Readers accept
  v1–v6; every new field None-safe, never defaulting to a value that
  looks measured.
- Version 0.6.0 → **0.7.0** in both pyproject and `__init__`; README
  version lines have tests — keep them green; README gains the tools
  family, the v2 loop instrument, the MoE fields, and a `## v0.7
  (v1.6)` history entry; the diff-ladder documentation gains
  `unsupported`.
- Budget worst-case comments recomputed for both modes (tools ~10
  calls; error script +2×runs).
- House testing discipline in full: TDD, mutation-checked load-bearing
  behavior under the pyc discipline, serialization round-trip +
  completeness for every new field, real-data acceptance anchored on
  committed artifacts, no GPU/network in the suite.
- Final live task (Task-12 pattern): tool probe against three
  tool-capable models plus one template-less model for a real
  `unsupported` capture; one error-script run; MoE metadata validation
  — transcripts committed under
  `docs/superpowers/evidence/tools-anchor/`.

## §6 Deferred, with rulings

- Sequential look-schedule for tools cells: deferred — two-turn cells
  don't map cleanly onto the single-call schedule; fixed-n is honest
  and named in the lens.
- Tool-choice forcing (`tool_choice: "required"`): deferred — assay
  measures unforced behavior everywhere; forcing measures the
  constraint (the black-oxide lesson).
- Multi-turn tool chains and parallel calls: v1.7-at-earliest, after
  the one-call question has live numbers.
- A text-protocol tools fallback for `unsupported` endpoints: ruled
  out for v1.6 (measures a protocol no consumer uses).
