`CallRecorder._write_row` does `open("a") -> write(one row) -> close` per call. On Linux, `write()` to a
regular file is atomic per-inode and `O_APPEND` makes the offset update atomic, so rows cannot interleave
regardless of size. **The lock is genuinely redundant for this write pattern on this platform** — not
wrong, just unexercisable.

Decision, three parts:
 1. KEEP the test. It pins a real property (under concurrency every row is present and whole) and would
    catch a FUTURE write-path change — a long-lived handle, or building a row incrementally — which is
    exactly the refactor that would make the lock load-bearing.
 2. FIX the docstring so it does not claim to prove the lock is load-bearing. A test that overclaims what
    it establishes is the defect class this whole instrument exists to refuse.
 3. Item 101 is only PARTIALLY closed: the concurrency case now exists; the lock remains unexercised.
    T12 records this with the platform reason.
This is the same shape as OVERLAP_TOLERANCE_S / item 16 — a guard kept and flagged rather than retired on
